# Release Process

Meridian ships continuously. There is no release train, no versioned
milestone builds, no branch cut. Trunk (`main`) is always deployable, and
every merge to `main` becomes a staging deploy within minutes and a
production candidate as soon as somebody clicks Sync in ArgoCD.

## Branching

- **Trunk-based.** No `develop`, no `release/*`, no long-lived branches.
- Feature branches live for hours, not days. If a branch is older than a
  week, ask why.
- Merge strategy: **squash and merge**. The PR title becomes the commit
  message on `main`.
- Force-push to `main` is disabled by branch protection everywhere.

## Feature flags (LaunchDarkly)

Anything that isn't safe to expose to all customers on the first canary
step ships behind a **LaunchDarkly** flag. Convention:

- Flag key: `<service>.<kebab-case-name>`, e.g. `beacon.cohort-v2-query`.
- Owner: a specific engineer, not a team, listed in the flag description.
- Default in prod: **off** until the owner is ready.
- Kill switch: every flag has a `kill_<flag>` companion that forces the
  legacy path even if the main flag is on. Use it in incidents.

Cleanup: flags older than 90 days at 100% rollout are surfaced in a
Slack digest to `#eng-flags`. The owner is expected to delete the flag
and the dead code path within a sprint.

## Release notes

Release notes are generated by the **`releasebot`** GitHub App from PR
titles. For customer-facing services (Portal, Beacon, Aurora) it opens a
weekly draft PR against `meridian/changelog` on Fridays.

Convention on PR titles so the bot categorises correctly:

- `feat(portal): add cohort v2 UI` — appears under **New**.
- `fix(ledger): dedupe on stripe webhook event.id` — appears under **Fixed**.
- `perf(beacon): index on cohort_events.workspace_id` — under **Performance**.
- `chore: ...`, `refactor: ...`, `test: ...`, `docs: ...` — omitted from
  customer notes; included in internal changelog only.

Engineering internally uses the same digest but with everything included.

## Deploy cadence

- **Staging**: every merge to `main`, automatically, within ~5 minutes.
- **Prod**: SRE or the on-call for a service clicks Sync in ArgoCD when
  ready. Typical services deploy 3–8 times a day during business hours.
- **Freeze windows**: Portal and Ledger observe a soft freeze on the last
  two business days of the month (invoicing) and the last week of the
  calendar year (Black Friday / holiday retail traffic). Emergency fixes
  are still allowed — see below.

## Emergency hotfix flow

When something is on fire in production and the normal PR-review-canary
cycle is too slow:

1. **Declare** the incident in `#eng-oncall` and page SRE if not already.
2. Open the fix as a PR from a `hotfix/<slug>` branch off `main`.
3. Get **one SRE approval** (any SRE). Normal branch protection stays on;
   we do not disable required checks. If CI is broken, that's a separate
   incident.
4. Merge. CD builds and pushes the image as usual.
5. Cherry-pick to a `hotfix/prod-<sha>` branch in `meridian/deploy` that
   only bumps the image tag for the affected service (no other collateral
   changes riding along).
6. Deploy directly with:

   ```bash
   argocd app sync <service>-prod --revision hotfix/prod-<sha>
   argocd app wait <service>-prod --health --timeout 300
   ```

   Then merge the `meridian/deploy` PR into `main` so ArgoCD returns to
   the normal Git-follows-main state.

7. Log the exact commands run and the outcome in **`#eng-oncall`** —
   this is the audit trail. The SRE who approved is on the hook for the
   post-incident write-up if the fix caused a follow-up incident.

The direct-sync-from-hotfix branch bypasses the usual "prod follows
`main`" invariant, and it must be reconciled back within an hour. If the
merge back to `main` doesn't happen before the next normal deploy, ArgoCD
will happily undo the hotfix on the next Sync.

## What we do NOT do

- No SemVer tags on service repos. The container tag is the git SHA;
  that's the identifier. (Libraries in `meridian/gh-actions` and
  `meridian/pyshared` do use SemVer tags — see their READMEs.)
- No manual QA gate. Automated tests + canary + Datadog error-rate
  analysis are the gate.
- No "release manager" role. On-call owns any deploy problem that lands
  during their shift.
