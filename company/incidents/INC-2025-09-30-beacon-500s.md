# INC-2025-09-30 — Beacon 500s on cohort endpoints

- **Severity:** SEV-3
- **Status:** Resolved
- **Detected:** 2025-09-30 11:38 PT via customer ticket from Forge
  Athletics + `dd:monitor/49183`
  (`beacon.http.5xx_rate{route:/v3/cohorts/*/members} > 2%`)
- **Resolved:** 2025-09-30 15:22 PT
- **PagerDuty:** PD-INC-F02244
- **Slack channel:** `#inc-2025-09-30`
- **Responders:** Elena Vasquez (IC), Jae-won Park (ClickHouse), Ravi
  Patel (consulted)

## Summary

Forge Athletics reported that their Portal cohort detail page had been
timing out and returning "Server error" for ~40 minutes. Beacon endpoint
`GET /v3/cohorts/:id/members` was returning 500 for a specific cohort
(`ck_forge_returning_high_value`, ~2.1M members). The endpoint's
underlying ClickHouse query was running 40+ seconds and eventually
being terminated by the FastAPI request timeout; before termination
it had also exhausted the upstream HTTP connection pool from Beacon
to `clickhouse-lb.mrdn.io`, causing sibling requests on
`/v3/cohorts/*/members` for other customers to also fail.

Root cause: the query builder in `beacon/queries/cohort_members.py`
did not append a `LIMIT` clause when the cohort definition included
a `NOT IN (subquery)` predicate. For most cohorts the ClickHouse
optimizer handles this efficiently. For Forge's specific cohort
shape (large negative predicate + high-cardinality property), the
optimizer chose a plan that scanned ~1.4B rows.

## Impact

- **Primary customer:** Forge Athletics — cohort detail page unusable
  for ~4 hours.
- **Secondary:** intermittent 500s on `/v3/cohorts/*/members` for ~9
  other workspaces due to connection pool exhaustion (~1% error rate
  during peak, from 12:15 – 13:40 PT).
- **Data loss / correctness:** None. Read-only endpoint.
- **SLO impact:** Cohort endpoint error-rate SLO (< 0.5%) breached
  for the day.

## Timeline (PT)

- **~11:00** — Forge Athletics opens Portal cohort page for
  `ck_forge_returning_high_value`. Beacon query starts, runs long.
- **11:11** — First 500 returned (FastAPI request timeout, 30s).
  ClickHouse query continues in background until server-side
  timeout (60s).
- **11:15 – 11:38** — Repeated attempts by Forge; each spawns
  another long ClickHouse query. Beacon → ClickHouse HTTP pool
  saturates.
- **11:38** — Forge opens ticket; `dd:monitor/49183` fires WARN.
- **11:45** — Elena paged. Joins `#inc-2025-09-30`.
- **12:05** — Jae-won pulls the ClickHouse query log for the
  offending query id; identifies scan-heavy plan.
- **12:35** — Short-term: added `SETTINGS max_execution_time=15,
  max_result_rows=1000000` at the ClickHouse client level for
  cohort-member queries in Beacon.
- **13:20** — Hotfix PR-6142 in `beacon-svc`: always append
  `LIMIT :page_size + 1` to `cohort_members` query regardless of
  predicate shape.
- **14:10** — Deployed via ArgoCD.
- **14:40** — Forge re-tested; cohort page loads in ~1.2s.
- **15:22** — Incident closed.

## Mitigation

1. Server-side `max_execution_time=15` on ClickHouse for cohort
   queries (defense in depth).
2. `LIMIT` always applied in `cohort_members` query builder.
3. Beacon → ClickHouse HTTP connection pool size increased 32 → 64
   as a headroom change.

## Follow-up

- Backlog: audit `beacon/queries/` for other query paths missing
  bounded `LIMIT`.
- Datadog monitor added: `dd:monitor/49221` — long-running ClickHouse
  query alert (any query > 10s).
- No formal postmortem written (SEV-3, single-customer impact).
  Lessons captured in this incident doc.
